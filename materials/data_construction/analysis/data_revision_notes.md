# 数据构造修订记录

## 证据与范围

本记录归纳 Java 文件生成样本、需求生成流程及其 SFT 转换。依据包括 [`scripts/remote/`](../scripts/remote/) 中归档的远程构造源码、构造器说明、当前 220 行任务三来源索引、1,226 行 SFT 来源索引及 [`data_statistics.json`](data_statistics.json)。我重新只读查看了 a6000 上的 JavaSampleBuilder、CoverageAnalyzer、JavaSkeletonExtractor、`build_sft.py` 和 sampler README；其 SHA-256 与本包归档副本一致。同时只读检查了本地 `didaima` 目录中的需求生成器、README 和 prompt。完整提示词归档于 [`reference/task3_requirement_prompt.txt`](../reference/task3_requirement_prompt.txt)，与需求生成器读取的 `prompt.txt` 逐字节一致。附录两个案例的目标源码均通过记录的 SHA-256 与仓库文件核对。远程检查使用只读文件读取及标准库 Python 内联分析，没有运行项目脚本或服务。

本实验的需求生成模型为 **gpt-6-luna**，这是用户对本次报告提供的确认。提示词文件本身不包含模型名；旧版 helper 快照与样本元数据中的模型字符串不一致，因此不以其中任一个作为本次模型的权威依据。

## 端到端构造流程

1. **候选仓库和领域标注。** 远程目录有 74 个仓库名条目、70 个去重后的 GitHub URL；当前克隆 10 个仓库，其中 9 个有当前任务三样本。仓库标记为企业信息化、智慧物流或智慧城市。Stars 是仓库目录元数据，但已检查的构造器和限定范围内文档没有固定的最低 stars 阈值，样本构造器也不按 stars 过滤。当前目录快照为 54–39,621 stars，3 个条目低于 100；当前克隆仓库的最低值为 140。这些观察值不能作为筛选阈值证据。

2. **Java 骨架提取。** Java AST 提取器扫描主源码侧的 Java 文件，排除测试、构建输出及生成代码目录。每个源文件生成仓库相对路径、包名、导入、声明类型、从完整源码提取的引用类型、源码哈希和不含方法体的 Java 骨架。构造器另行发现主源码和测试源码，用于建立候选目标与相关测试的关联。任务三独立于任务一、二的方法级样本构造。

3. **文件候选与依赖闭包。** 任务三从主源码中的 Java 类建立候选；候选需有相关测试和对应骨架记录。输出目标是完整源文件，但覆盖率键是目标类。如果同一路径下多个类均可成为候选，则按路径去重并保留合并类覆盖率较高的候选。样本骨架列表先放目标骨架，再递归收集源码引用到的项目内类型依赖骨架。测试源码用于关联候选与测试，不作为代码生成目标。

4. **合并覆盖率筛选与训练专用扩样。** 对每个候选类，把其关联且成功运行的测试所命中的可执行行合并后计算行覆盖率。任务三候选只有在合并后的类级覆盖率**严格大于 0.50**，且至少有一个关联测试覆盖目标行时才通过。因此，监督目标是完整文件，但筛选指标是类级覆盖率，不是整文件覆盖率。启用 `--mix` 时，还可为未进入可测候选的骨架化主源码类添加 `only_sft_train` 样本；这些样本不要求通过上述覆盖率筛选，标记为仅训练用途，且 `tests` 为空。扩样上限按仓库计算，为 testable 样本数乘以领域倍数：企业信息化 1 倍、智慧城市 4 倍、智慧物流 1 倍。当前 SFT source set 中有 703 条此类记录，全部在 train。

5. **中文需求生成。** 需求生成器读取任务三草稿，对已有非空 `requirement` 的记录予以保留；缺失需求时，将仓库标识、目标路径、目标文件骨架、依赖骨架及目标文件完整参考源码组成中文提示词，交由 gpt-6-luna 生成。提示词明确规定：完整源码是行为依据，骨架用于结构和依赖边界；需求需覆盖文件/模块职责、所有类型与成员的签名和行为、关键 API 调用、参数与返回值约束、处理流程、异常/边界、状态、副作用和集成约束。输出须按 `文件职责、依赖、模块行为、符号行为、API 调用、异常与边界、集成约束` 顺序组织为中文自然语言，不输出 JSON、代码块、Java 源码或伪代码。压缩展示版见 [`reference/task3_requirement_prompt_display.md`](../reference/task3_requirement_prompt_display.md)，完整原文见 [`reference/task3_requirement_prompt.txt`](../reference/task3_requirement_prompt.txt)。

6. **需求回填。** helper 安全解压任务三草稿包，校验仓库身份和相对目标路径，并从本地仓库副本定位目标源码；只生成空需求。若单条生成失败，该条仍为空，处理继续。只有仓库内需求全部非空时，才会上传该仓库样本；服务器端校验上传 JSON 及目标路径后替换 `3.json`。当前 220 条文件样本的需求字段均非空。

7. **SFT 输入与目标。** SFT 构造器对每个目标 Java 文件生成一条记录，使用目标源码哈希校验本地文件与样本记录一致。`source` 是完整参考 Java 源码；`prompt` 中以注释形式嵌入详细需求，并要求生成该文件的完整 Java 源码。需要区分存储的依赖信息和实际送入模型的骨架：任务三样本保存完整依赖骨架闭包，需求生成器也会使用目标骨架和依赖骨架；当前 LowCode SFT prompt renderer 对骨架候选去重后只渲染 `similar_code[0]`。因为目标骨架在闭包列表首位，SFT prompt 实际包含目标骨架，而不是完整依赖闭包。当前提示中的响应标记为 `The complete Java source begins below:`。不能据此宣称它与 Jinan v4 的实际 prompt 逐字一致；v4 应按其自身训练记录分析。

8. **训练与共享留出评估来源。** 构造器按原始样本在每个仓库内确定性地抽取共享留出评估来源：单仓目标量为 `floor(该仓库样本数 / 5)`，伪随机种子由 42 和仓库名组成，`only_sft_train` 样本不进入留出来源。因此一个仓库可以同时含训练和共享留出记录；这不是按整个仓库留出的划分。来源索引的原始 `train/eval` 标签对应 984 条训练数据与 242 条共享留出记录；703 条 `only_sft_train` 和 281 条普通记录在训练数据，242 条留出记录均为普通记录。当前功能实验最终保留220条任务三样本（企业信息化76、智慧物流102、智慧城市42），全部命中共享留出来源、没有命中训练数据；另有22条留出记录未保留为功能评测有效样本。训练期间评估与文件级功能评测复用这一留出来源，不把220条描述为训练样本，也不将242条解释为另一份独立留出集合。该对应关系由 Java ID 和源码哈希核验。

## 正文与附录的信息分工

正文需说明候选与测试关联规则、类级合并覆盖率阈值、可选训练专用扩样、基于完整源码和骨架生成需求、当前 SFT prompt 实际使用目标骨架、完整文件监督目标，以及训练数据与共享留出评估来源的关系。若报告讨论仓库热门度筛选，应说明未发现固定 stars 下限。原始索引标签、逐仓库计数、样本 ID、源码节选、完整提示词、源码哈希和提示词实现细节放入附录或工程材料；图表与可复用绘图代码已随本包保存。

该任务的监督目标是**完整 Java 文件**，不应称为函数级生成。方法/类 AST 用于候选和覆盖率分析，任务一、二也有方法级样本，但任务三每个样本监督一个完整目标文件。
