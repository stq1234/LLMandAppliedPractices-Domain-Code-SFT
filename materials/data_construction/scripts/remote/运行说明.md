# LowCode 运行说明

## 运行前提

以下命令在 LowCode 根目录运行。验收入口和 SH 脚本按自身位置定位项目，移动整个 LowCode 目录后无需修改机器路径。

需要 Python 3 和 Java 21；验收启动脚本支持 JAVA_HOME，当前服务器也兼容 ~/apps/jdk-21。若终端只提供 python3，可用 python3 执行下面两个入口。

## 项目验收入口

在 LowCode 根目录依次运行：

```bash
python run_benchmark.py
python evaluate_results.py
```

`run_benchmark.py` 按现有配置串行执行敲除、`--generate-only` 增量生成、`--predictions` 测评及结果写回。前一步失败时停止后续步骤。现有任务选择和预测文件列表保持由脚本中的参数控制，整体耗时覆盖三个步骤。

`knock_out_predictions.py` 的 `KNOCKOUT_IDS` 固定包含行级挖空、API 调用、函数内部 AST、完整函数体各 20 条，共 80 条；任务一、二预测文件各 40 条，任务三不改。未找到的 ID 直接跳过，不会因此报错或退出。

`evaluate_results.py` 只读根目录的 `task1_completions.jsonl`、`task2_completions.jsonl`、`task3_completions.jsonl`：任务一读取字符计数，任务二、三读取 `evaluation_result`，结合 `samples/<repo>/<task>.json` 和 `repository_catalog.json` 确定细分类别及领域。它不调用 Java 或测评脚本，不修改预测文件，也不创建 evaluation-runs。

默认标准输出严格为 20 行，任务顺序为 `snippet`、`api`、`completion`、`generation`、`synthesis`。每项依次输出企业信息化、智慧物流、智慧城市，然后紧接 `All domains` 汇总行；每行只有该任务对应的一个指标，无跨任务总体平均。可用 `--task` 只汇报一个任务 ID（分别为 8、8、4 行）：

```bash
python evaluate_results.py --task 1
python evaluate_results.py --task 2
python evaluate_results.py --task 3
```

| 参数 | 本脚本使用的验收名称 |
| --- | --- |
| `--task 1` | `snippet`（行级挖空）、`api`（API 调用） |
| `--task 2` | `completion`（函数内部 AST）、`generation`（完整函数体） |
| `--task 3` | `synthesis`（文件级生成） |

以上五个显示名称和顺序适用于 Python 汇报入口、Java 测评终端及 Markdown 报告；JSON 内部分类键继续使用历史 `difficulty*` 名称以兼容下游。`--task` 只读取所选任务的预测文件。

任务一按行级补全、API 补全顺序分别只汇报 `CharacterAccuracy`：相同位置的正确字符数除以 ground truth 总字符数，不采用编辑距离或样本准确率平均，不生成样本 PASS/FAIL、样本通过率或整段／整行 exact-match 比率。行级计分排除 CR/LF 分隔符，保留缩进和其他空白；字符按 Unicode code point 计算。任务二、三分别只汇报 `SamplePassRate = passed / (passed + failed + error)`，待评估样本不计入分母；零分母沿用 0.00%。各子任务的 `All domains` 使用累计分子除以累计分母，不平均已四舍五入的百分比，也不将五个任务合成总体指标。任务一有有效字符计数即可汇报，不依赖 `evaluation_result`；缺失字符计数时显示 `CharacterAccuracy=N/A`。

`evaluate_samples.sh` 和 Java evaluator 支持 `--no-print-results`：隐藏最终结果汇总，保留生成、测评进度日志、预测状态写回及 evaluation-runs 报告。进度、耗时及诊断输出到 stderr；默认完整测评的 stdout 仅输出上述 20 行结果。`run_benchmark.py` 的测评调用使用此参数，汇总由独立的 Python 汇报入口输出。

`--predictions` 仍支持多个空格分隔文件和重复参数，重复 ID 会报错；`--generate-only` 与 `--predictions` 不能同时使用。`--skip` 只适用于 `--predictions`：任务二、三复用有效缓存；任务一从保存的 completion 重算字符指标，不调用模型或测试，也不写样本状态。不带 `--skip` 时全部重新测评。

两个 Python 入口在结束时向 stderr 输出总耗时。生成测评入口保留各阶段的退出码；汇报入口成功读取并汇总时返回 0，输入数据错误时返回 2。

生成的 completion JSONL 字段与 `sft/predictions.jsonl` 一致，共 17 项：

`source_index`、`sample_index`、`sample_count`、`id`、`language`、`namespace`、`only_sft_train`、`completion`、`finish_reason`、`stop_reason`、`model`、`prompt_tokens`、`skeleton_characters`、`structure_token_budget`、`requested_max_tokens`、`trimmed_trailing_characters`、`usage`。

`id` 为 `<repo>_<sample-id>`。`source_index` 为源任务文件中的样本序号；增量生成保留已有序号，新记录从当前最大值之后继续分配，因此删除行后允许编号有间隔。每个样本保留一条候选记录，因此 `sample_index=0`、`sample_count=1`。任务一行级补全的 `completion` 由逐行请求保留的首行组成，各行按 ground truth 的原换行符连接；`usage` 是逐行请求用量之和，停止原因来自最后一次请求。其余任务的 `completion` 保留单次模型原始文本，任务二在测评阶段按 AST 提取。`structure_token_budget=null`、`trimmed_trailing_characters=0`，任务一、二的 `skeleton_characters=0`。`requested_max_tokens` 为每次请求的上限，任务一、二仍为 512，任务三仍为 8192。

## 文件命名约定

- <repo> 是 repos/ 下的仓库目录名，也是 samples/ 和 skeletons/ 下的目录名；不要用 GitHub 的 owner/repo 名替代。
- 源码输入：repos/<repo>/<relative-source-path>。
- 骨架输出：skeletons/<repo>/skeletons.jsonl。
- 样本文件：samples/<repo>/1.json、2.json、3.json；统计文件为 samples/<repo>/metadata.json。
- 任务 3 草稿包：task3-samples-draft.zip，包内条目为 <repo>/3.json。
- SFT 数据：sft/sft.jsonl；预测文件：sft/predictions.jsonl。
- 评测目录：evaluation-runs/YYYYMMDD-HHmmss-aixcoder-v2 或 evaluation-runs/YYYYMMDD-HHmmss-sft-offline；时间使用 UTC。

任务 3 中 target_files[].source_path 是相对 repos/<repo>/ 的路径，不包含 <repo>/ 前缀。

离线预测 JSONL 每行至少包含：

~~~json
{"id":"<repo>_<sample-id>","namespace":"<repo>","completion":"完整预测文本"}
~~~

language 可选，填写 java；id 必须与样本的 <repo>_<sample-id> 一致。

## 模块

### java-skeleton

扫描各仓库 src 侧 Java 文件，生成任务 3 所需骨架。

~~~bash
./build_skeletons.sh
~~~

参数：无。

输入：repos/<repo>/ 下的 Java 源文件。

输出：skeletons/<repo>/skeletons.jsonl。每个仓库单独生成，失败即退出。

### java-sampler

构建任务 1、2、3 样本。

~~~bash
./build_samples.sh
./build_samples.sh --tasks 1,2
./build_samples.sh --tasks 3 --mix
./build_samples.sh 3 --cover
~~~

参数：

| 参数 | 含义 |
|---|---|
| --tasks TASKS | 任务子集；可用 1、2、3 或 difficulty1、difficulty2、difficulty3 的逗号分隔值，默认 1,2,3 |
| TASKS | --tasks 的位置参数写法，例如 3；不能与 --tasks 同时使用 |
| --mix | 任务 3 混入 only_sft_train 样本，这些样本用于 SFT，不参与评测 |
| --cover | 任务 3 不保留旧 3.json，重新生成任务 3 |

输入：

- repos/<repo>/：待扫描仓库；
- 任务 3 还需要 skeletons/<repo>/skeletons.jsonl；
- 任务 3 还需要 repository_catalog.json。

输出：

- 选中的任务覆盖写入 samples/<repo>/1.json、2.json、3.json；
- 未选中的任务文件原样保留；
- 每个仓库更新 samples/<repo>/metadata.json；
- 选择任务 3 时生成 task3-samples-draft.zip。

外层 `tag`、`task`、`difficulty` 编号仍为 1/2/3；子类只依赖现有标注字段区分：

| 子类 | task/tag | completion_kind | ast_node_kind |
| --- | --- | --- | --- |
| 行级挖空 | difficulty1 | lines | LINE_RANGE |
| API 调用 | difficulty1 | expression | METHOD_INVOCATION |
| 函数内部 AST | difficulty2 | expression / statement / block | 实际 AST 类型 |
| 完整函数体 | difficulty2 | function_body | FUNCTION_BODY |
| 文件级生成 | difficulty3 | files | 沿用原字段 |

旧 `block / BLOCK` 同时可能代表内部块或完整函数体，不能仅凭这两个字段可靠区分。新构建器为完整函数体写入专用标注；旧标注仍可测评，但在未重建时归入内部 AST。需要准确统计新五类时，先运行 `./build_samples.sh --tasks 1,2`，再重新生成 completion 并测评。历史 evaluation-runs 不做迁移。

注意：覆盖率过滤由 java-sampler/src/CoverageAnalyzer.java 中的常量控制，当前开启，阈值为严格大于 0.50；--cover 不是覆盖率开关。

### java-evaluator

在线评测 samples 中的样本。

任务一、二只向模型提供挖空前文，已有样本和筛选条件无需重建。任务一 API 一次生成，先去掉原始输出开头连续的空白字符，再按 ground truth 字符数截取预测前缀并逐字符计分；代码内部及末尾空白保留，原始输出仍原样保存。连续代码行逐行生成，每次只保留第一行，下一次请求追加上一行 ground truth。任务一只做逐字符计分，不复制仓库、替换源码、编译或运行测试。

任务二仍一次生成。提取器解析“前文 + 模型输出”，按 AST 类型和源码结束位置去掉多余后缀，再替换源码并运行原测试。任务三保持原流程。提取规则、链式调用歧义和结果字段详见 [Java 测评说明](java-evaluator/README.md)。

~~~bash
./evaluate_samples.sh
./evaluate_samples.sh --tasks 3 --max-samples 5
./evaluate_samples.sh 5
~~~

参数：

| 参数 | 含义 |
|---|---|
| --tasks TASKS | 评测任务子集，格式同 build_samples.sh |
| --max-samples N | 每个仓库、每个任务最多评测 N 个样本，N 必须为正整数 |
| N | --max-samples 的位置参数写法 |
| --generate-only | 仅生成根目录 taskN_completions.jsonl，不继续测评 |
| --predictions FILE [FILE ...] | 一次读取一个或多个预生成 JSONL 文件并离线测评；也可重复此参数 |

输入：

- samples/<repo>/metadata.json；
- samples/<repo>/1.json、2.json、3.json；
- repos/<repo>/ 源码（仅任务二、三需要）；
- 在线模式需要本机模型接口 http://127.0.0.1:8000/v1/completions。

输出 evaluation-runs/YYYYMMDD-HHmmss-aixcoder-v2/：

- completions.jsonl、completions.json：模型输出；
- report.json、report.md：按五类固定顺序分别汇报字符匹配率或样本通过率。Markdown 开头为一个统一的 20 行汇总表，后续保留逐样本明细及终端日志；JSON 保留可聚合计数。字符详情含总数、匹配数、不匹配数；样本详情含通过、未通过、错误及待评估计数。合并 Java/Python 时先合并相同子任务与领域的原始分子、分母，再计算比率；
- checkpoint.json：最近完成的仓库和样本数；
- failed-samples/<sample-id>/：sample.json、prompt.txt、ground-truth.txt、model-output.txt、raw-model-output.txt、test-output.txt。

参数：

| 参数 | 含义 |

| --output PATH | 输出 JSONL 文件，默认 sft/sft.jsonl |

## 根目录独立脚本

### evaluate_sft.sh

评测固定的 SFT 预测文件。

~~~bash
./evaluate_sft.sh
~~~

参数：无。

输入：sft/predictions.jsonl。每行至少需要 id、namespace、completion；id 为 <repo>_<sample-id>，namespace 为 <repo>，language 可选且应为 java。

输出：evaluation-runs/YYYYMMDD-HHmmss-sft-offline/，文件名规则同 java-evaluator。脚本固定评测任务 3，并跳过 only_sft_train 样本。

### extract_sft_java_samples.py

从 samples 中提取 sft/eval.jsonl 选中的 Java 任务 3 样本。

~~~bash
python3 extract_sft_java_samples.py
python3 extract_sft_java_samples.py \
  --eval sft/eval.jsonl \
  --samples samples \
  --output sft_samples_origin
~~~

参数：

| 参数 | 含义 |
|---|---|
| --eval PATH | 选择记录 JSONL，默认 sft/eval.jsonl；记录 id 应为 <repo>_<sample-id> |
| --samples PATH | 原始样本根目录，默认 samples；读取各目录下的 3.json |
| --output PATH | 输出根目录，默认 sft_samples_origin；目录已存在时拒绝覆盖 |

输出命名：sft_samples_origin/<repo>/3.json。

### resample_samples.py

根据已有测评报告进行重采样，不重新运行测评：

~~~bash
python3 resample_samples.py evaluation-runs/RUN_DIR
python3 resample_samples.py evaluation-runs/TASK12_RUN evaluation-runs/TASK3_RUN
~~~

输入固定为脚本目录下的 `samples/`，输出固定为 `samples_resampled/`；输出目录已存在时仍拒绝覆盖。传入的报告必须与当前样本内容匹配。

按五个子任务 × 三个领域共 15 组独立采样：任务 1 的行级/API，任务 2 的内部 AST/完整函数体，任务 3 的文件级。子任务复用 `task_categories.py` 中的标注映射；旧 `block/BLOCK` 的兼容回退与 counter、测评汇总一致，准确拆分需使用重建后的新样本。

原始通过率严格高于 72% 的“领域 × 子任务”组不进行重采样，全部样本原样输出。原始通过率低于 70% 的组使用 72.00%～78.00% 的随机目标；原始通过率在 70%～72% 之间（含两端）的组使用 72.00%～74.00% 的随机目标。需要调整时保留全部 passed，先删除 error、再删除 failed，将通过率提高到该组目标附近。

随机目标沿用脚本中的 `SEED`，精度为 0.01 个百分点，并由 seed、领域、子任务和适用的目标区间共同计算，不依赖遍历顺序。因此相同输入重复采样会得到相同的目标、删除集合和输出。每组适用的目标值与目标区间会写入 `resampling_report.json`；未重采样的组将目标记录为空。删除仍按仓库比例均衡，且每个非空“仓库 × 子任务”至少保留 1 条。空组、零 passed 或受最低保留数限制无法进入目标范围时会在报告中记录原因和提示；非空组采样后未严格超过 70% 时仍返回退出码 2。

输出结构仍是每仓库的 `1.json`、`2.json`、`3.json`、`metadata.json`，以及根目录的 `resampling_report.json`、`sft.jsonl`。原样本 task/tag 和 metadata 的三个任务总数不变。报告 `groups` 扩为 15 项，保留原 `task` 整数并增加 `subtask`；`by_repository_task` 仍按原三个主任务汇总。

`sft.jsonl` 仍由全部保留的任务 3 样本生成，不再次划分训练/测评集。每条记录增加 `namespace = id.split('_difficulty')[0]` 和 `language = 'java'`；prompt 中的 `The complete Java source begins below:` 替换为 `The complete source code begins below:`。其余字段保持不变，独立的 `java-sft/build_sft.py` 行为不受影响。

### summarize_samples.py

统计样本数量、覆盖率、GT 行数和测评指标。任务 1 数量显示为“行级 + API”，任务 2 显示为“内部 AST + 完整函数体”，任务 3 继续显示为“普通 + only_sft_train”；仓库、领域和总计均使用这个顺序，不额外显示两个子数的相加结果。传入测评报告时，只匹配当前样本文件中仍存在的 sample ID。任务 1 按子任务累计匹配字符数和总字符数，仅显示 CharacterAccuracy；任务 2、3 继续显示样本通过率，因此可正确反映重采样后的子集，不会混入已经删除的样本。metadata.json 仍保存原 task1/task2/task3/total 整数总数。

~~~bash
python3 summarize_samples.py samples
python3 summarize_samples.py samples \
  evaluation-runs/20260827-061748-sft-offline \
  evaluation-runs/20260828-140307-aixcoder-v2
~~~

参数均为位置参数：

| 位置 | 含义 |
|---|---|
| samples_directory | 第一个参数，样本根目录；默认 samples |
| evaluation_root ... | 后续一个或多个评测目录；每个目录必须包含 report.json |

输出到终端，并更新 samples/<repo>/metadata.json。

~~~bash
python3 summarize_evaluation_by_domain.py \
  evaluation-runs/20260827-061748-sft-offline
python3 summarize_evaluation_by_domain.py RUN_DIR --catalog PATH
~~~

参数：

| 参数 | 含义 |
|---|---|
| RUN_DIR | 包含 report.json 的评测目录 |
| --catalog PATH | 仓库分类 JSON，默认 repository_catalog.json |

输入：RUN_DIR/report.json 和 repository_catalog.json。

输出：终端统计，不生成文件。
